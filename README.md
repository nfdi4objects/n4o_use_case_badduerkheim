# n4o_use_case_badduerkheim
Data and Software for the AG "Use case Bad Dürkheim"

## Convert CSV to CIDOC-CRM RDF

`csv2rdf.py` converts a UTF-8 CSV file into RDF using RDFLib. The input
follows version 1.1 of the community standard for cultural heritage objects
(KEO), the mapping is specified in [`docs/mapping_cidoc_crm.md`](docs/mapping_cidoc_crm.md)
(in German). The field delimiter defaults to `,` as the standard requires and
can be changed with `-d` or `--delimiter`.
Turtle is the default serialization format; other installed RDFLib serializer
formats are available through the command-line option.

Install the dependencies:

```sh
python3 -m pip install -r requirements.txt
```

Run the tests with:

```sh
python3 -m unittest discover -s tests -v
```

Two further tests check the output against the CIDOC CRM, GeoSPARQL and BIBO
ontologies. They run when `CRM_RDF_AP` points to a clone of the application
profile:

```sh
git clone https://github.com/nfdi4objects/crm-rdf-ap ../crm-rdf-ap
CRM_RDF_AP=../crm-rdf-ap python3 -m unittest discover -s tests -v
```

Convert the sample data:

```sh
python3 csv2rdf.py data/Kulturerbeobjekte_Knowledge_Graph.csv
```

The N-Triples and JSON files in `data/` are produced with:

```sh
python3 csv2rdf.py data/Kulturerbeobjekte_Knowledge_Graph.csv -f nt
python3 csv2json.py data/Kulturerbeobjekte_Knowledge_Graph.csv > data/Kulturerbeobjekte_Knowledge_Graph.json
```

The tests check that these files match the output of the scripts.

By default, the output is written beside the input file with a `.ttl` extension.
Choose the serialization format, output path, and namespace for generated
identifiers with:

```sh
python3 csv2rdf.py input.csv --format json-ld --output output.jsonld \
	--base-uri https://data.example.org/kulturerbe/site/
```

For a tab-separated file, specify the tab delimiter:

```sh
python3 csv2rdf.py input.tsv -d "$(printf '\t')"
```

Use `python3 csv2rdf.py --help` to list the serializer formats registered in
your RDFLib installation. When `--output` is omitted, the file extension is
chosen for the selected format.

By default, identifiers generated by the mapping use the namespace
`https://example.org/keo/`, a placeholder until a permanent namespace is
chosen.

Each CSV record becomes a `crm:E31_Document` that documents the cultural
heritage object, a `crm:E18_Physical_Thing`. Names are `skos:prefLabel`,
identifiers are typed `crm:P1_is_identified_by` nodes with `rdf:value`,
descriptions are `crm:E33_Linguistic_Object` and types are `crm:P2_has_type`.
Dating bounds form one EDTF literal at `crm:P4_has_time-span` of an
`crm:E5_Event`, which also refers to the epochs. WKT geometries are attached
to an `crm:E53_Place` using GeoSPARQL. The WKT literal starts with the IRI of
its CRS, and the coordinates follow the axis order GeoSPARQL expects. Problems
in the data are reported as warnings on stderr. All non-empty CSV fields are
also retained as literal properties in the `keo:` source-data namespace.

## Sparql API
The current Sparql endpoint is: 
```
https://graph.nfdi4objects.net/dev/api/sparql 
```
Here are some simple examples (shell) for public data access with Sparql commands:
```sh
curl --data-urlencode 'query=DESCRIBE <http://example.org/collections/1>' -G https://graph.nfdi4objects.net/dev/api/sparql
```

```sh
curl --data-urlencode 'query=SELECT * WHERE { GRAPH <http://example.org/collections/1> { ?s ?p ?o } } LIMIT 100' https://graph.nfdi4objects.net/dev/api/sparql
```
